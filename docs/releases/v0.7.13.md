## Added

### Scenario V2 contract

The [Recipe development guide](../developer/recipes-development.mdx) describes these supported contracts.

- Scenario documents use the explicit string schema version `"2"`.
- Each Scenario V2 document identifies a stable scenario ID.
- A scenario declares its goal separately from its Plan template.
- Typed parameters describe the inputs needed for instantiation.
- Applicability requirements describe when the scenario may be used.
- The Plan template uses the existing numeric compact Plan schema version `2`.
- Optional summaries provide concise scenario descriptions.
- Optional descriptions retain longer author guidance.
- Unknown scenario fields fail validation instead of becoming implicit behavior.
- A Recipe cannot introduce a separate approval lifecycle.
- A Recipe cannot introduce an independent execution state machine.
- Multi-WorkItem templates declare their validation references explicitly.
- Producer-output input edges participate in the shared dependency validation.
- Dependency cycles fail the same Plan validation used by ordinary tasks.
- Recipe manifest API compatibility and Scenario API compatibility are checked separately.
- V2 use requires explicit API negotiation rather than reinterpretation of historical V1 records.

### Parameter binding

- String parameters retain string values without coercion.
- Integer parameters require safe integer values.
- Boolean parameters require actual boolean values.
- Repository-path parameters distinguish filesystem paths from ordinary text.
- Parameter names must be unique.
- Required parameters must be bound before instantiation.

- Binding lists preserve duplicate names so duplicate input is rejected.
- Unknown binding names are rejected.

- Boolean strings do not satisfy boolean parameters.
- Supported semantic text fields can use single-pass `{{name}}` substitution.
- Nested substitutions are rejected.
- Unresolved substitutions are rejected.
- Path substitutions require repository-path parameters.
- Command text is not a parameter substitution surface.
- Check and capability identifiers remain stable rather than templated.
- WorkItem, dependency, and output identifiers remain stable rather than templated.
- Absolute repository-path bindings are rejected.
- Drive-qualified and UNC paths are rejected.
- Traversal and repository escape paths are rejected.

- Parameter bindings are not a supported channel for retaining secrets.
