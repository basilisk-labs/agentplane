## Invariants

Repository mode is policy. The selected task route is lifecycle authority. Workspace allocation is
a separate physical-execution decision.

Use these rules in CLI, runtime, runner, evaluator, verification, finish, PR, and integration code:

1. Do not read `ctx.config.workflow_mode` to choose task lifecycle behavior.
2. Do not infer workspace isolation from `direct` or `branch_pr`.
3. Do not run two writable agents in one checkout.
4. Load task lifecycle state through `TaskCommandContext`.
5. Pass `TaskExecutionContext` to route-sensitive APIs.
6. Use `WorkspaceAllocationContext` for physical execution and cleanup.
7. Use `TaskExecutionContext.base_ref` and `base_sha` for diff, quality, verification, and finish.
8. Keep absolute workspace paths out of semantic identities.
9. Block undeclared external capabilities before runner invocation; retain post-run observation as
   defense in depth.
10. Integrate direct candidates through the serialized queue, never by concurrent base writes.
11. Compile one approved plan and execution scope into one task-local `ExecutionGrant`.
12. Resolve side-effect authority from the active grant before consulting repository fallback
    policy. A user-derived grant may authorize `task.scope.extend` only when every requested
    repository effect is already allowed by the approved execution contract.
13. Derive a short-lived `OperationLease` from the active grant for each provider mutation and
    embed it in the existing expiring, state-scoped authority journal.
14. Invalidate the grant when the normalized plan digest or material execution-scope digest
    changes. Compiler-derived writable-root changes do not invalidate an otherwise identical
    semantic scope.

## Loading sequence

Task commands use a two-phase load:

1. read the minimal task route identity;
2. resolve selected mode against repository policy and task risk/effects;
3. locate the route-authoritative task workspace or snapshot;
4. reload authoritative task state;
5. build the final immutable `TaskExecutionContext`.

Do not emulate this by cloning or mutating repository config.

Task creation freezes `task_execution_context.base_ref` and `base_sha` from the creation checkout,
or from an explicit `task create --base` ref. Runtime checkout paths are discovered dynamically and
must not be persisted as semantic identity.

## Plan approval transport and grants

`task advance --agent-json` chooses one approval transport:

- `host_user_decision` when the embedding host is the user-provenance boundary;
- `signed_user_receipt` when trusted receipt issuers are configured.

Both transports bind the decision to the current task, normalized plan digest, and route state
fingerprint. Approval persists an `agentplane.execution_grant` extension containing the plan and
scope digests, stable logical repository identity, logical-completion contract digest, evidence
provenance, actor, and compiled capabilities. Repository identity is derived from immutable Git
root objects and therefore survives branch changes and directory relocation. Manual `--by` remains
an operator compatibility/bootstrap surface.

The supervisor may resolve lifecycle and provider approval steps from an active grant. It may also
apply an exact writable-root extension when the request remains inside the approved repository
effects. A new effect, changed plan/material scope digest, human question, external wait,
effect-in-doubt recovery, or terminal attention still stops execution. Existing state-bound
side-effect records carry the exact grant-derived `OperationLease`; parsing and execution reject a
tampered, expired, cross-task, cross-operation, or state-scope-mismatched lease. Stable lease ids
make a crash replay reuse the existing authority record instead of issuing duplicate authority.

## Route and capability changes

`auto` is the creation default. High-risk effects, material uncertainty, or the repository
`branch_pr` floor can raise a direct preference to `branch_pr`. Preserve reason codes, implementation
commit, changed paths, and evidence when escalation happens so the branch supervisor can continue
from a handoff instead of repeating implementation.

When a known direct runner request includes network or external side-effect capability, stop before
adapter creation with `side_effect_requires_isolation`. Re-resolve the route and reuse the preserved
implementation only after branch authority is established.

## Verification and finish

Generated `PLANNER fallback scaffold` checks receive one deterministic compatibility recovery: if
a declared `bun run <script>` target does not exist, verification selects an existing project-native
test script and records both the declared and executed commands. This recovery never applies to
explicit non-fallback Verify Steps.

New lifecycle qualification requires verification input v4. Older records are audit-only. Consume
the assessment object rather than a boolean so the CLI can report the exact invalidation reason and
recovery action.

Finish loads task execution authority before planning. Its closeout journal progresses through
`prepared`, `task_state_written`, `close_commit_written`, and `completed`; failures persist
`recovery_required`. Recovery must resume or reconcile that journal rather than guessing whether a
partial close succeeded.
