# Canonical final-validation timing exception

A canonical task can retain a `FAILED` final-validation result when one declared command completed its functional checks but exceeded a suite time budget. The normal route is to repair the failure and run validation again. After exact-head hosted checks succeed, a USER operator can accept one bounded timing-only failure without changing the original result to `PASSED`.

The operator action is `ap task final-validation accept-timing <task-id>`. It requires the current canonical record digest, the retained failure-evidence digest, the exact failed command, a positive maximum overage in milliseconds, the hosted change request number, source branch, implementation head SHA, and `--outcome-report <base64url-json>`. The report is a structured USER attestation with the exact task, plan, failed evidence, command and implementation identities, budget and duration in milliseconds, aggregate functional counts, and the complete expected list of required hosted checks. Functional failures and incomplete checks must both be zero; the total must equal passed plus skipped. The accepted overage cannot exceed 5% of the declared budget or 60 seconds, whichever is smaller.

The command reads the immutable final-validation artifact and checks that every declared command ran, exactly one exited with status 1, and that its output has one explicit `suite budget exceeded: duration=...s budget=...s` marker matching the structured report. The stdout/stderr tails alone cannot prove the aggregate functional result; the USER attests to the structured counts. It re-observes the change request and requires every hosted check, including every report-declared required check, for that exact implementation SHA to succeed. For GitLab, the newest listed exact-head pipeline must itself be successful, and the pipeline and job inventories must fit in their complete fetched pages. It rejects stale task state, changed implementation, other check failures, pending effects, missing evidence, and broader timing overages.

Without approval arguments, the command only prints the exact state-bound `final_timing_exception` request and its digest. When trusted USER receipt issuers are configured, one issuer must sign that request; re-run with `--approval-receipt <base64url-receipt>`. The command verifies signature, issuer, task, state, operation and scope digests, and expiration before retaining the receipt. When no trusted issuer is configured, the native manual operator route requires `--by USER --approval-request-digest <exact-printed-digest> --note <reason>`. It retains a separately labeled `manual_operator` decision bound to the request, note, and current state. This manual route records explicit operator attribution and is not cryptographic authentication. Agents must return control at this USER decision boundary and must not manufacture the operator decision during a semantic episode.

Acceptance creates a separate `final_timing_exception` on the Task Kernel record. `final_validation.status` remains `FAILED`; the operational verification projection is `accepted_timing_exception`. The approved plan, failed evidence, command and environment identities, repository fingerprint, hosted head, complete required hosted-check list, hosted-check evidence, and USER attribution are retained. Later route checks require every retained hosted job name to remain successful for the same head. Normal `ap task advance <task-id> --agent-json` resumes canonical completion after acceptance. This route applies only after hosted evidence exists; it does not waive a failed test or create a synthetic local PASS.
