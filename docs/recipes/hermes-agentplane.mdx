# Hermes Agentplane recipe

## What does it do?

The Hermes Agentplane recipe adds prompt policy for repositories that dispatch Agentplane work
through Hermes Kanban worker lanes.

It keeps the boundary explicit:

- Hermes owns dispatch/run lifecycle: queue, assignee, claim, run id, retries, crash detection,
  comments, dashboard, and human handoff.
- Agentplane owns engineering task lifecycle: task README/frontmatter, plan approval,
  branch/worktree, verification, PR/integration, finish, and ACR evidence.

## When should I use it?

- Hermes Kanban is the durable operational board for a repository.
- Multiple agents or lanes may work against the same repository.
- `branch_pr` should protect checkout, branch, verification, and integration boundaries.
- Hermes cards should close only after Agentplane terminal evidence validates.

## When should I not use it?

- The repository does not run Hermes Kanban.
- The task is a single local direct-mode helper run.
- The Hermes runtime cannot provide lifecycle callbacks or an external worker lane adapter.

## Command to apply

```bash
agentplane recipes install hermes-agentplane
agentplane recipes add hermes-agentplane
agentplane recipes explain hermes-agentplane
```

For new repositories that should avoid Codex as the default task runner, initialize with the Hermes
tool profile:

```bash
agentplane init --quick --tool hermes
```

That profile keeps the normal Agentplane policy gateway and configures `agentplane task run` through
the `custom` runner adapter with `runner.custom.command=["hermes","agentplane","run"]`.

## Expected adapter commands

```bash
agentplane init --tool hermes --workflow branch_pr --yes
agentplane hermes doctor --json
agentplane hermes enqueue <task-id> --board <board> --assignee agentplane-coder --json
hermes agentplane supervise --task-id <task-id> --root <repo>
hermes agentplane approve --task-id <task-id> --root <repo>
agentplane task run <task-id>
agentplane hermes lifecycle comment --body '<structured projection>' --json
agentplane hermes lifecycle complete --body 'Agentplane terminal evidence validated' --json
```

`--tool hermes` configures `runner.default_adapter=hermes`, disables IDE-specific sync, and writes
`runner.custom.command=["hermes","agentplane","run"]`. The Hermes runtime image must provide that
command; Agentplane does not fall back to Codex for Hermes task execution.

## Runtime environment

Hermes worker lanes must pass these variables to Agentplane-side commands:

```bash
AGENTPLANE_HERMES_LANE_REGISTRY=/opt/agentplane/lane-registry.json
AGENTPLANE_HERMES_ALLOWED_ROOTS=/workspace/repo
AGENTPLANE_HERMES_PLUGIN_PROTOCOL=agentplane.hermes.plugin.v2
AGENTPLANE_HERMES_NATIVE_WORKER_LANE_API=1
AGENTPLANE_HERMES_APPROVAL_RECEIPT_BRIDGE=1
HERMES_KANBAN_TASK=<hermes-card-id>
HERMES_KANBAN_BOARD=<board>
HERMES_KANBAN_RUN_ID=<run-id>
HERMES_KANBAN_WORKSPACE=<repo-workspace>
HERMES_KANBAN_CLAIM_LOCK=<claim-lock>
```

`agentplane hermes doctor --json` fails closed unless the v2 plugin capability, native lane API,
trusted approval-receipt bridge, lane registry, binaries, `branch_pr`, and non-empty root allowlist
are proven. It separately reports
whether the current worker claim is complete. An empty root allowlist denies every workspace.
Task-runner invocations also export `AGENTPLANE_RUNNER_TASK_ID` when the run target is an Agentplane
task, so Hermes launchers can bind the external worker run back to the canonical task id.

The trusted Hermes host reads the base64-encoded Ed25519 PKCS8 DER signing key from
`AGENTPLANE_HERMES_APPROVAL_PRIVATE_KEY_PKCS8`; the plugin never forwards that variable to worker or
LLM subprocesses and emits the bridge capability only after loading a valid key. Configure
`approval_issuer`, `approval_subject`, and `approval_ttl_minutes` in the plugin settings, then pin
the matching doctor-reported public key under
`authority.approval_receipts.trusted_issuers` in Agentplane.

## Visibility contract

`agentplane hermes enqueue` and the compatibility `agentplane hermes supervise` projection return a
`hermes_comment_projection` packet. Hermes plugins should post that packet before block or
complete transitions. The packet includes:

- Agentplane task id, revision, status, verification state, and current route phase.
- Route blockers and the next typed action.
- Runner visibility commands: `agentplane task run status`, `inspect`, and event `logs`.
- Evidence references for the task README, ACR, and runner artifacts.
- The authority boundary that keeps Hermes status projection-only.
- A canonical `agentplane.hermes.terminal-attestation.v1`; only `terminal/done` permits root-card
  completion.

## Safety model

The recipe does not make Hermes a task backend for Agentplane. Hermes board state is a projection.
Agentplane task state remains canonical and Git-visible. The Hermes plugin performs all LLM work by
consuming bounded PLANNER, EXECUTOR, and EVALUATOR `WorkOrder` episodes; it never synthesizes formal
Agentplane transitions from prose.

## Unattended Hermes operation

Hermes should keep performing the LLM work while AgentPlane remains the invisible formal control
plane. After the user approves the primary plan, configure repository authority when a Hermes lane
must progress through routine PR publication boundaries without showing lifecycle prompts:

```yaml
authority:
  mode: policy
  actor: POLICY:hermes
  allow_operations:
    - pr.open
    - pr.head.publish
    - pr.artifacts.update
    - pr.sync_or_verify
    - provider.pr.refresh
    - route.remote.refresh
  deny_operations:
    - integration.enqueue
    - task.pre_merge_close
  ttl_minutes: 10
  approval_receipts:
    trusted_issuers:
      - id: hermes-dialog
        public_key_spki: <base64-der-spki>
    max_ttl_minutes: 10
    clock_skew_seconds: 30
```

Hermes consumes fresh `task advance --agent-json` packets and performs only `agent_episode`
objectives. AgentPlane resolves allowed policy boundaries internally, performs formal transitions,
and returns the next semantic packet. The primary plan approval remains a mandatory user boundary.
After that approval, Hermes surfaces another user action only when the current operation is absent
from the allowlist, present in the denylist, is a provider merge decision, or the state-bound
authority can no longer be reconstructed safely.

## Conversational user approval

The Hermes bridge may execute an approval command after the user decides in the Hermes dialogue;
the user should not have to copy state digests into a terminal. This does not authorize Hermes or
the model to manufacture user authority.

When `task advance --agent-json` returns `approval_required`, its `operator_action` contains an
`approval_receipt.request` bound to the current task, authority reference, state fingerprint, and,
for a side effect, the exact operation digest and state-scope digest. A trusted bridge outside the
LLM must:

1. authenticate the user and display the exact pending decision;
2. record an explicit approval in the dialogue;
3. sign a short-lived `agentplane.user_approval_receipt` with its configured Ed25519 identity;
4. replace `<base64url-receipt>` in the supplied `operator_action.argv` and execute that argv;
5. request a fresh action packet instead of replaying the previous command.

Agentplane verifies the issuer, signature, exact route binding, expiry, configured TTL, and
single-use evidence digest. The stored actor is derived as `USER:<subject>@<issuer>` and remains in
the authority audit. A forged, stale, expired, wrong-scope, or replayed receipt fails closed.

The first semantic plan is still a user-owned decision. `authority.mode=policy|all` applies only to
eligible side-effect operations after plan approval; it cannot satisfy plan approval or provider
merge. A provider-merge packet deliberately has `operator_action.argv=null`: the bridge must keep
that decision in its operator/provider executor boundary rather than translating it into a generic
side-effect grant.

With this split, Hermes performs all LLM work, Agentplane advances the formal lifecycle and allowed
effects invisibly, and the user is asked again only for drift, denylisted or unconfigured effects,
provider merge, destructive or credential boundaries, or a state that cannot be recovered safely.
