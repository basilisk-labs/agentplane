# Clean Task Core rebuild specification

## Outcome

Agentplane must have one canonical Task state machine that owns Task, plan, WorkItem, authority,
validation, effect, and completion decisions. Repository documents, CLI status, provider records,
and legacy task fields are projections or adapter inputs. They are not independent lifecycle truth.

The rebuild succeeds when:

1. a pure kernel deterministically evaluates every canonical transition;
2. every mutation is bound to one task, plan revision, WorkItem, authority envelope, state
   fingerprint, implementation identity, and idempotency key;
3. legacy tasks migrate once with byte-exact backup, deterministic classification, readback, replay,
   and rollback evidence;
4. all production routing, verification, evaluation, completion, and effect scheduling use canonical
   state only;
5. self-hosting, crash recovery, repository migration, and release qualification pass without
   manual task or journal edits.

This specification does not replace the public CLI, context system, provider clients, release
tooling, or documentation system. It replaces their lifecycle authority boundary.

### Target dependency rule

The dependency direction is:

```text
CLI / runner / provider / migration commands
                 |
                 v
       application supervisor
                 |
                 v
       canonical Task kernel
```

The kernel may import only deterministic core utilities, schemas, and domain values. It must not
import Node filesystem, child process, Git helpers, provider clients, task documents, CLI code,
backend implementations, clocks, randomness, environment variables, or legacy conversion.

Adapters may depend on the kernel. The kernel must never depend on adapters. Architecture checks
must enforce this direction before M2 begins.

## Canonical kernel contract

### Inputs

Every kernel evaluation receives explicit immutable inputs:

```ts
type KernelInput = Readonly<{
  aggregate: TaskAggregate;
  command: TaskCommand;
  actor: ActorIdentity;
  authority: ExecutionAuthority | null;
  repositoryFingerprint: Sha256Digest | null;
  occurredAt: string;
  mutationId: string;
}>;
```

`occurredAt` and `mutationId` are adapter-supplied values. The kernel must not call a clock or UUID
generator. Replaying the same input must return the same output bytes.

### Commands

The closed command union covers at least:

- capture Task intent;
- propose, reject, and approve a plan revision;
- materialize a WorkItemGraph;
- claim, begin, accept result for, validate, rework, block, resume, complete, or cancel one WorkItem;
- record final validation;
- prepare, observe, reconcile, or supersede an external effect;
- amend a plan without authority expansion;
- request approval for a material authority delta;
- evaluate and complete a Task;
- record controller transfer and migration receipts.

No command accepts free-text Task status as transition authority. Free text may be carried as a
comment or summary after the transition is decided.

### Outputs

The kernel returns one of:

```ts
type KernelResult =
  | {
      kind: "accepted";
      aggregate: TaskAggregate;
      events: DomainEvent[];
      receipts: MutationReceipt[];
    }
  | { kind: "rejected"; code: KernelRejectionCode; facts: string[]; requiredAction: string | null };
```

Rejections are data. Expected lifecycle conflicts, stale fingerprints, missing authority, incomplete
dependencies, stale validation, and uncertain effects must not be represented by generic thrown
errors.

### Mandatory invariants

1. **Single canonical state:** a mutable Task has exactly one canonical aggregate and revision.
2. **Legal transitions:** every Task and WorkItem transition belongs to a closed transition table.
3. **Plan binding:** active WorkItems belong to the current approved plan revision and digest.
4. **One result target:** every normal semantic result identifies exactly one Task and one WorkItem.
5. **State binding:** results, approvals, reviews, validation, and effects bind to the state
   fingerprint they observed.
6. **Authority subset:** child or replacement authority is equal to or narrower than its active
   parent grant across repository, scope, effects, capabilities, resources, risk, reversibility,
   validation, policy, and completion contract.
7. **User provenance:** derived authority never claims `USER` provenance. Material expansion emits a
   delta-only user decision request.
8. **Idempotency:** a repeated mutation ID returns the existing receipt and produces no second event
   or effect.
9. **Output integrity:** a WorkItem cannot complete without every declared output manifest from that
   WorkItem and the required validation result.
10. **Validation identity:** deterministic evidence binds to implementation identity, check ID,
    normalized command, toolchain digest, and relevant environment digest.
11. **Effect safety:** a non-idempotent effect in an unknown state blocks replay until provider
    readback or explicit reconciliation resolves it.
12. **Completion:** Task completion requires an approved current plan, all required WorkItems and
    outputs, current final validation, and no pending or uncertain effects.
13. **Projection impotence:** documents, legacy status, verification text, PR metadata, and provider
    summaries cannot authorize a transition.
14. **Determinism:** equivalent normalized inputs produce byte-identical state, events, reason codes,
    and receipts.

## Adapter contracts

### Persistence

The repository port must provide either compare-and-swap or serialization, atomic state-plus-event
write, atomic plan materialization, and idempotency receipts. A backend missing any required
capability cannot execute autonomous mutations.

Every write sequence is prepare, persist atomically, read back, compare digest, then expose a
receipt. Partial projection failure may be repaired from canonical state and cannot roll back a
committed canonical transition.

### Documents and status

One projector renders task documents, list output, brief output, status, verification summaries,
reviews, comments, and commit summaries from canonical state. Projection repair changes no
canonical revision or implementation identity. Task discovery resolves the same canonical task
from base and task-owned worktrees.

### Git and workspace

Git and workspace adapters observe exact repository identity and return typed effect results. They
do not choose lifecycle transitions. Commit identity excludes operational task metadata, review
files, verification files, provider snapshots, and closeout data.

### Validation and evaluator

Validation adapters execute exact declared checks and return evidence. They do not mark WorkItems or
Tasks complete. Evaluator results bind to a frozen implementation identity and selected WorkItem;
semantic changes stale prior review while operational metadata changes do not.

### Provider effects

Push, PR creation/update, queueing, merge, hosted close, publish, and cleanup use the same effect
protocol: `prepared`, `issued`, `observed_applied`, `observed_not_applied`, `effect_in_doubt`,
`reconciled`, or `superseded`. Intent persists before the call. Retry performs provider readback
first. Publication binds to an exact SHA and immutable artifact digests.

### Legacy migration

Legacy parsing is isolated from the kernel and production route. It returns one of:

- a deterministic canonical migration plan;
- a read-only archived terminal manifest;
- a typed quarantine result with exact ambiguous fields;
- a typed unsupported-schema result.

It never returns a guessed aggregate.

## Migration algorithm

For each Task:

1. Read the source bytes and record their digest, backend identity, repository identity, and schema.
2. Classify the source as canonical, legacy active, legacy terminal, malformed canonical, ambiguous
   legacy, or unknown schema.
3. Preserve a byte-exact backup before any mutation.
4. Build a deterministic plan without timestamps except receipt metadata.
5. Map legacy `TODO`, `DOING`, and `BLOCKED` to `PLANNING` with no invented plan, WorkItem, output,
   approval, review, or verification.
6. Map legacy `DONE` to a read-only archived manifest; do not recreate mutable completion evidence.
7. Split legacy `required_inputs` into typed context sources and upstream output IDs only when
   classification is unambiguous. Quarantine ambiguity.
8. Validate schema, graph, dependencies, authority, transition, and projection invariants.
9. Atomically write canonical state and one migration receipt.
10. Read the result back and compare the expected digest.
11. Re-run migration and prove that it returns the existing receipt without byte changes.
12. Prove receipt-scoped rollback restores the exact original bytes and does not revert unrelated
    later Tasks.

Dry-run reports every classification, proposed digest, ambiguity, and rollback capability. Apply
stops on any ambiguity or unsupported layout. Bulk migration is canary-first and does not continue
after the first unexplained mismatch.

## Replay corpus manifest

M2 must freeze inputs and expected normalized outputs for these families:

| Family           | Required cases                                                                                                             | Required assertion                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Canonical kernel | Every legal transition and representative illegal edge                                                                     | Exact aggregate, event, receipt, and reason-code equality                         |
| Legacy lifecycle | `TODO`, `DOING`, `BLOCKED`, `DONE`, unknown status                                                                         | Deterministic migration or exact quarantine code; no invented evidence            |
| Plans            | pending, approved, rejected, stale digest, non-material amendment, material expansion                                      | Approval and authority remain digest-bound; only material expansion asks the user |
| WorkItems        | dependency chain, fan-out, conflicting resource claims, rework, stale result, duplicate result                             | Readiness and receipt equality; no duplicate result application                   |
| Required inputs  | source paths, artifact IDs, ambiguous strings, missing upstream output                                                     | Deterministic classification or quarantine                                        |
| Validation       | focused, full, hosted, stale identity, changed toolchain, missing executable                                               | Evidence cannot satisfy a stronger or different requirement                       |
| Evaluator        | pass, rework, blocked, human-required, semantic drift, metadata-only drift                                                 | Review freshness follows implementation identity                                  |
| Effects          | not issued, applied, not applied, timeout before/after application, uncertain, reconciled                                  | No duplicate external effect and exact recovery route                             |
| Workspaces       | base checkout, task worktree, missing document in frozen worktree, divergent head                                          | Same canonical Task identity and fail-closed mutation path                        |
| Backends         | local, serialized direct, cloud fake, interrupted atomic write                                                             | Equal canonical state and receipt semantics                                       |
| Task classes     | direct, branch PR, context, release, batch                                                                                 | Shared kernel rules with adapter-specific effects only                            |
| Crash points     | creation, plan, approval, claim, result, validation, commit, review, completion, PR, merge, hosted close, publish, cleanup | Restart reaches one safe route with no lost WorkItem or repeated effect           |

Each fixture records source bytes, source digest, implementation identity where applicable, command
sequence, expected events, expected aggregate digest, expected projection digest, expected effect
state, and expected next-action reason code. Capture and replay use an exact Git anchor and a clean
isolated checkout.

## Dual-run and cutover

Dual-run is comparison-only. The legacy path remains authoritative until the M2 gate passes. The
new path receives the same normalized read input but cannot write or call providers. A mismatch
records both digests, the first divergent event or field, source identity, and reproduction command.

Cutover order:

1. read-only status and route projections;
2. plan and WorkItem lifecycle in isolated fixtures;
3. local backend writes;
4. cloud fake backend writes;
5. verification and evaluator flows;
6. Git and provider effects under readback protection;
7. context and release task classes;
8. repository corpus migration;
9. self-hosting controller transfer;
10. legacy production import removal.

Every step has a feature-independent rollback receipt. Do not keep a permanent feature flag that
allows mutable legacy authority after M3.

## Milestone acceptance gates

### M0: specification

- The code map names domain, adapters, effects, projections, tests, and legacy entry points.
- The kernel contract and mandatory invariants are complete.
- Migration, replay, dual-run, rollback, and cutover are explicit.
- Every old roadmap Task has one disposition in the traceability matrix.
- Documentation IA and formatting checks pass.

### M1: isolated kernel

- The new module imports no filesystem, process, Git, provider, CLI, backend, document, or legacy
  code.
- All legal transition tables and invariant rejection codes have deterministic vector tests.
- Replaying the same command returns the same bytes or the same existing receipt.
- Authority subset comparison covers every declared dimension and preserves user provenance.
- Graph readiness, result targeting, validation identity, effects, and completion are kernel rules.
- `bun run test:fast`, `bun run typecheck`, and `bun run arch:check` pass.

### M2: adapters and migration

- Local and cloud fake backends satisfy the same atomicity and idempotency contract.
- New Tasks are canonical at creation; unmigrated active Tasks cannot mutate implicitly.
- Dry-run, apply, replay, quarantine, and byte-exact rollback pass for the full migration fixture set.
- Dual-run produces zero unexplained mismatches across the replay corpus.
- Documents and commands are projections from canonical state.
- Validation, evaluator, Git, and provider adapters cannot decide lifecycle state.
- Fast tests, typecheck, architecture checks, and lifecycle invariants pass.

### M3: cutover and retirement

- The repository Task corpus migrates with receipts and remains inspectable.
- Production routing contains no synthetic aggregate, legacy status conversion, text-plan authority,
  legacy verification completion, DONE-first finish, or duplicate approval/scope truth.
- Crash injection passes at every listed boundary for direct, branch PR, context, release, local, and
  cloud fake paths.
- Twenty sequential self-hosting Tasks complete with zero manual task edits, journal edits, bypasses,
  lost WorkItems, or duplicate external effects.
- Three clean release drills agree on source SHA, package digests, tag, hosted release, registry, and
  installed CLI behavior.
- Full local CI and required hosted exact-head checks pass.

### Recovery projection rule

When a legacy task-level implementation already produced outputs for an approved WorkItem graph,
recovery must not infer Task completion from those files or from task-level verification. It must
bind each existing output to the matching required WorkItem, validate that WorkItem, persist its
output manifest and receipt, and advance the dependency graph in order. Task-level closure becomes
eligible only after every required WorkItem reaches `COMPLETED`; an unbound or optional WorkItem
result cannot substitute for that projection.

The scheduler contract treats `required_inputs` as upstream output-manifest IDs. Repository source,
legacy task records, policy, and other readable material belong in the WorkItem context manifest;
they must not be encoded as `required_inputs`, because no producer can satisfy those narrative
labels. A root WorkItem therefore has an empty `required_inputs` list, while dependent WorkItems
name only outputs declared by their predecessors.

## Stop and rollback rules

Stop and request a plan refinement when:

- the new kernel needs a side-effect dependency;
- a legacy input cannot be classified deterministically;
- dual-run has an unexplained state, event, receipt, route, or projection mismatch;
- a child authority would exceed its parent;
- a provider effect cannot be read back;
- implementation changes the public CLI or task format beyond the declared compatibility boundary;
- a retained context or release task is mistakenly treated as a duplicate;
- hosted evidence is not bound to the exact reviewed head.

Do not continue by adding another lifecycle, scheduler, Program entity, hidden fallback, implicit
migration, manual state edit, or approval inferred from task prose.
