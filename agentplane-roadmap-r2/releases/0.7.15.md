# Agentplane 0.7.15: Workflow modes and shared feature deliveries

Status: planned milestone; atomic implementation decomposition and runtime qualification pending.

Release position: the next planned patch after 0.7.14. This document adds scope to the [release roadmap](../agentplane-0.7.9-0.7.14-roadmap-r2.md). It does not claim that the proposed behavior is implemented or authorize execution, publication or merge.

## User outcome

A user can choose where a change is developed and group multiple sequential tasks into one feature delivery on an explicitly selected branch. Completing one task does not publish or close an unfinished feature. AgentPlane prepares a pull request only when the whole delivery is ready and publication authority is present.

## Workflow modes

| Mode        | Working location                                                                  | Completion and publication                                                                                                 |
| ----------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `direct`    | Pin the current user-selected branch and its repository identity before mutation. | Complete the task on that branch. Do not switch branches or merge implicitly.                                              |
| `branch`    | Isolate work on a selected feature branch from an explicit configured base.       | Complete local work without requiring a PR. Merge requires separate authority.                                             |
| `branch_pr` | Use the same isolated branch and explicit base model.                             | Create a PR only after delivery-level local readiness and explicit publication authority. Merge remains a separate action. |

These are repository-effect modes around the existing Kernel-backed coordinator. They do not introduce separate task reducers, Recipe execution engines or schedulers.

## Selection and authority

1. Honor explicit user selection within repository policy. Reject a prohibited or unsupported selection with an actionable explanation.
2. When joining an existing delivery, retain its pinned mode, branch and base. An explicit conflicting request requires resolution before mutation.
3. When no selection exists, use policy constraints, isolation needs, risk, uncertainty, reversibility and concurrency to select the least costly allowed route. Use bounded semantic judgment where interpretation is required; the CLI validates formal constraints.
4. Freeze the validated selection before mutation. Resume the same selection after restart. A route or branch change requires an explicit authorized transition.

Task completion, delivery closure intent, PR publication and merge are distinct decisions. A Recipe, model result or successful check cannot supply user authority. Existing approval, verification and independent review rules remain enforced. Optional EVALUATOR omission remains subject to the qualifications defined for 0.7.14; this milestone adds no exemption and works with review required.

## Shared feature delivery

- Bind each member task explicitly to one delivery with a pinned branch, base and workflow mode. Support multiple sequential tasks on the same selected feature branch.
- Preserve each task's Plan, scope, verification evidence and lifecycle identity. Delivery coordination must not become a second owner of task lifecycle state.
- Track required membership and explicit delivery closure intent. Finishing a member cannot infer that no more work is expected.
- Require all required members to satisfy their completion obligations, a clean workspace, current aggregate checks and closure intent before PR creation.
- Bind readiness evidence to the current delivery membership and code state. Membership changes or new code invalidate affected readiness evidence.
- Prevent duplicate publication across retries and concurrent callers. Preserve unresolved-effect stops and reconcile observed provider state before retrying.
- Keep merge permission separate from both local readiness and PR creation. Do not merge or clean up a shared branch while required members still depend on it.

3. Route intake, continuation and recovery through the common coordinator. Add current-branch semantics for `direct` and the isolated `branch` mode.
4. Add shared delivery readiness and PR publication admission with aggregate checks, explicit closure and durable effect accounting.
5. Qualify installed-package behavior, migration and recovery. Update CLI help, workflow documentation and framework policy templates together with runtime support.

## Compatibility and release gates

- Preserve existing task, approval, Plan and evidence history. Preview migration before incompatible writes. Unknown or ambiguous old records stop for explicit resolution.
- Do not reinterpret historical `direct` records as current-branch authority. Preserve their original meaning until an explicit supported conversion exists.
- Document unsupported older writers, format changes and downgrade limits. A patch version label is not proof of backward compatibility.
- Qualify all supported entrypoints and modes against one coordinator. Policy text must not advertise unsupported CLI operations as available behavior.
- Verify a multi-task delivery in which the first task completes while the delivery remains open; the final ready delivery produces at most one authorized PR.
- Verify that missing members, absent closure intent, dirty workspaces, failed or stale aggregate checks, route conflicts and absent publication authority block PR creation.
- Verify that restart preserves the chosen branch and mode, concurrent admission cannot duplicate effects, and member completion cannot imply merge or premature branch cleanup.
- Verify ordinary single-task work and Recipe-created tasks retain their scope, approval, review and recovery guarantees.

Release requires focused positive, negative and recovery evidence plus the repository's installed-package and release checks for the exact candidate. Document functional results separately from any measured efficiency claim.

## Scope exclusions

Scenario V2 remains the 0.7.13 scope. Qualified EVALUATOR omission remains the 0.7.14 scope. This milestone excludes a separate Recipe workflow engine, automatic Recipe publication, generalized task memory, broad review disabling and a new autonomous merge policy.

The [execution charter](../EXECUTION-CHARTER.md) continues to define authority, evidence, compatibility and effect-safety constraints. This milestone does not move later capabilities into earlier release dependencies.
